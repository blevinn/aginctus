# Herdr SSH credential lifecycle

Status: proposed design; credential generation, guest delivery, rotation, and host-trust reconciliation are not implemented by this document. Paths and orchestration contracts below are proposed internal interfaces.

## Purpose and current state

Define how Aginctus generates and deploys SSH credentials for the dedicated Herdr client to connect to managed workloads. This implements the identity responsibilities in [Architecture](architecture.md) and [ADR 0001](adr/0001-herdr-client-topology.md), within the [first Herdr milestone](milestones/0001-herdr-console.md).

Today, `internal/incus/client.go` creates and reconciles the Herdr client container, its root disk, and management NIC. It does not provision SSH credentials or machine entries. `flake.nix` supplies a root-run Herdr service in the client image and an `agent`-run Herdr service plus SSH server in the OpenCode image. The workload disables password authentication, keyboard-interactive authentication, and root SSH login, and contains no authorized client key.

The design must work without ambient host SSH configuration, private keys in images, or a database. Containers come first; VMs use the same contract when the Incus guest agent can provide authenticated exec and file operations.

## Decisions and trust boundaries

- Use one Ed25519 client keypair per deployment. Generate it inside the Herdr client and retain the private key there. Only public material crosses the Incus API to workloads.
- Each workload generates its own SSH host keys on first boot. Images must contain no host private keys; image validation must enforce this.
- Bootstrap authorization and host trust through authenticated Incus API operations, not through an initially unverified SSH connection.
- Authorize only workloads explicitly enabled for this client's console, using the non-root account defined by the workload contract (`agent` for OpenCode).
- Pin host public keys and keep strict verification enabled. Network discovery supplies addresses, never trust.
- Treat the Incus daemon, its administrators, Aginctus orchestration, and the client container as privileged infrastructure. An Incus administrator can execute commands or read guest files; keeping keys guest-local does not protect against that administrator.

Compromise of the deployment client key grants the workload account's privileges on every authorized workload. The account can control its Herdr sessions and agent processes. Per-workload client identities, SSH certificates, hardware-backed keys, and automatic expiry are deferred. Gateway credentials have a separate lifecycle and must not share this key or provisioning state.

## Material and ownership

| Material | Generated by | Stored at | Delivered to |
| --- | --- | --- | --- |
| Client private key | Guest helper in client | Client-only credential directory | Nothing outside client |
| Client public key and fingerprint | Derived from client private key | Client and deployment metadata | Selected workload authorization files |
| Host private keys | Workload SSH bootstrap | Workload's SSH host-key directory | Nothing outside workload |
| Host public keys and fingerprints | Derived from workload host keys | Workload and client trust manifest | Client `known_hosts` |
| Target address, login account, stable host alias | Aginctus runtime discovery | Client generated configuration | Herdr/SSH client |

Use `/var/lib/aginctus/ssh` for client credential state, owned by the runtime identity (initially root). Directories are `0700`; private keys are `0600`. Store generation directories under `identities/<generation>/`, containing `id_ed25519` and its derived public key. A manifest records the deployment ID, active and pending generations, fingerprints, target incarnation IDs, and rotation phase. It contains no private key. Store the manifest privately and update it atomically.

Incus metadata records stable deployment and workload IDs and a workload incarnation token, in addition to existing Aginctus ownership markers. Names and addresses are not identities. A normal restart preserves the incarnation; an explicitly orchestrated recreation assigns a new one. This extends the current ownership schema and must precede credential delivery. Validate project, deployment, role, instance type, and incarnation on every read or write. Refuse foreign collisions and unexpected deployment IDs; adoption must be a distinct explicit lifecycle operation.

Do not put private keys in Incus configuration, cloud-init, Jsonnet inputs, rendered plans, Nix derivations, the Nix store, command arguments, logs, or host temporary files. Incus exec requests may run fixed guest helper operations; keys must never be interpolated into shell strings. Validate names and public keys and use structured file/API operations.

## Generation and persistence

Once the owned client is running, invoke a fixed guest helper through the Incus Go API. It acquires a deployment credential lock, verifies state ownership, and creates the first Ed25519 key with the guest OS cryptographic random source only when no identity exists. Install OpenSSH client tooling and this helper in the client image as implementation prerequisites.

The private key has no passphrase because the client must connect unattended and no separate unlocking service exists in the MVP. Restricted guest permissions and protection of the entire client root disk, snapshots, and backups are the corresponding controls. Do not forward a user SSH agent or reuse a human key.

Derive the public key from the stored private key on every reconciliation and compare its fingerprint to the manifest. Reject malformed, mismatched, or unexpectedly missing key state rather than silently generating a replacement. Generation uses an exclusive temporary directory, verifies the pair, and atomically publishes it before recording the active generation. An interrupted initial generation can recover its verified directory; it must never replace an existing identity.

The initial storage policy uses the client root disk. Stop/start retains identity; client deletion destroys it. A future separate credential volume can change that policy deliberately. Client snapshots and backups include credentials and require equivalent access controls; restoring an old snapshot must not automatically reauthorize a retired key. Public generation metadata on workloads is checked against restored client state, and discrepancies require explicit recovery.

## Initial deployment sequence

The following ordering is mandatory. A target is published to Herdr only after its SSH probe succeeds.

1. Reconcile the management network, owned client, and explicitly enabled workloads. Wait for running state and the required Incus guest operations. Keep SSH on the management path; guest firewall and Incus network policy must prevent unintended ingress. Network attachment alone is insufficient evidence of isolation.
2. Verify ownership and deployment IDs; acquire a deployment-scoped orchestration lock. Ensure or read the client identity through its guest helper, returning only the public key, fingerprint, and generation.
3. For each target, verify its incarnation and login account. Install the deployment's public key into its dedicated authorization file through authenticated Incus file/exec operations. Read back and verify the managed content and permissions.
4. Wait for the workload to generate host keys and start SSH. Read host public keys through authenticated Incus guest operations, validate their format, and record the expected fingerprints against the workload incarnation.
5. Discover the target's management address from Incus runtime state. Generate explicit SSH target configuration and `known_hosts` entries with a stable alias derived from deployment and workload IDs.
6. Stage client trust and configuration files, check syntax and permissions, and publish them atomically as one configuration generation. Reject a known incarnation whose host key unexpectedly changed.
7. From inside the client, probe SSH with batch authentication, the selected identity, strict host verification, and a bounded timeout. Check the intended login identity and Herdr availability without starting agent work. Publish successful targets in generated Herdr machine configuration; mark other targets unavailable with a precise provisioning phase.

Use direct Incus Go client operations, following the adapter boundary; do not shell out to the host `incus` CLI. If a VM's guest agent is absent or unready, provisioning stops with a capability/readiness error. No password, public SSH, or trust-on-first-use fallback is allowed.

## Workload authorization contract

The initial NixOS guest module should configure a root-owned runtime `AuthorizedKeysFile`, such as `/var/lib/aginctus/ssh/authorized_keys/%u`, in addition to any explicitly supported administrator authorization source. The guest helper owns only its deployment's file content, refuses symlinks and unsafe directories, validates each key, and uses temporary-file-plus-rename publication on the same filesystem. Directories are root-owned and traversable by sshd; authorization files are root-owned `0644`. They hold public material and must never be writable by `agent`.

A file contains only the active generation and, during rotation, the pending generation, each identified by deployment and generation in a comment. Comments assist diagnostics; identity and reconciliation use parsed key bytes and recorded fingerprints. Never overwrite unrelated administrator keys or authorize the client for root. Removal of console access deletes only Aginctus's authorization.

Disable agent, TCP, and Unix-socket forwarding, X11 forwarding, user RC execution, and tunnel creation for this managed login path. Preserve PTY and command execution required by Herdr; a forced command is deferred until Herdr's exact invocation contract is verified. Confirm the pinned Herdr version works with these restrictions before rollout. This is control access to the workload account, not a sandbox against commands run as that account.

## Client configuration and host trust

Aginctus owns a dedicated SSH config and `known_hosts`, independent of `/root/.ssh`, user agents, and host configuration. Each generated target specifies:

- the discovered management `HostName`, port, and workload `User`;
- `IdentityFile` pointing to the active generation and `IdentitiesOnly yes`;
- `IdentityAgent none` and `BatchMode yes`;
- `StrictHostKeyChecking yes`, a dedicated `UserKnownHostsFile`, and `GlobalKnownHostsFile /dev/null`;
- a stable `HostKeyAlias` and `UpdateHostKeys no` so network responses cannot expand managed trust;
- forwarding disabled as above.

Provision only the host key algorithms the client policy permits. Ed25519 is the initial required host algorithm. Never use `ssh-keyscan` as the source of trust or set `StrictHostKeyChecking=no`/`accept-new`.

Address changes regenerate connection data while preserving the alias and pinned host key. An unexpected host-key change for the same incarnation blocks connection even if the public key was fetched through Incus; it requires an explicit host-key replacement operation. An orchestrated workload recreation has a new incarnation, removes the old trust entry, and bootstraps fresh trust through Incus. Revalidate incarnation immediately before publication and probing to avoid trusting a replacement created during reconciliation.

Implementation must inspect the pinned Herdr SSH invocation/configuration format and prove it honors this dedicated configuration, including host alias and known-hosts settings. If Herdr cannot select a config file, a managed SSH wrapper with fixed arguments or an upstream change is required. Machine-entry field names and wrapper choice remain an integration gate; do not claim host verification from configuration Herdr never consumes.

## Reconciliation and orchestration integration

Keep resource creation in the existing Apply/Compose drivers. Add a typed runtime `ssh-access` driver for credential bootstrap, delivery, probing, and cleanup. This is a proposed addition, not an existing driver. Its plan contains only deployment/instance references, selected accounts, desired console access, and an operation such as reconcile or rotate. It resolves key material and realized addresses after resource steps complete; Jsonnet never sees private keys or runtime guest contents.

Validate the entire plan before mutation, as required by [Declarative orchestration](orchestration.md). Structural validation checks references and account/path policy; runtime readiness checks happen after instances exist. Run resource, credential, and machine-publication steps sequentially and fail-fast. Do not add a second bespoke workload `ensure` path.

Dry-run performs read-only discovery and reports missing identities, authorization changes, trust mismatches, and planned probes. It generates no keys, starts no guests, writes no files, and invokes no mutating helpers. When prerequisites do not exist, report planned bootstrap with unknown runtime fingerprints. A workflow containing a driver without dry-run capability still fails at the engine's existing capability gate.

Repeated reconcile preserves valid identities and host trust, repairs owned authorization/configuration drift, and leaves foreign files untouched. Bound operation timeouts and never log helper streams containing secret material. Concurrent reconciles must serialize across host processes using a deployment-scoped lock in the client guest; helper file locks also protect generation. Scope excludes concurrent operators on multiple Incus hosts. If the client is unavailable, fail before credential mutation.

## Rotation, revocation, and recovery

Normal rotation uses a persisted, resumable state machine in the client manifest:

1. **Prepare:** create a pending generation in the client without changing the active identity. Snapshot the authorized target set and incarnations in the manifest.
2. **Distribute:** authorize both active and pending public keys on every target. Probe the pending key explicitly with `IdentitiesOnly` so success cannot come from the old key. A failed or offline target prevents activation; retry from recorded state.
3. **Activate:** after all targets pass, atomically publish configuration selecting the pending identity and record it as active. Suspend new Herdr connections during this local publication; recover a crash by comparing the selected configuration generation with the manifest.
4. **Retire:** remove the old public key from every target and verify removal before deleting its private key and clearing rotation state. An unreachable target leaves retirement pending. Never report completed rotation while an old key remains authorized.

Do not start a second rotation while one is pending. Workloads added during rotation receive the generation set required by the recorded phase and must pass the relevant probe before publication. Removed workloads must have authorization revoked (or their owned instance deleted) before being dropped from the retirement inventory.

Revocation prevents new authentications; existing SSH connections and multiplexed sessions may remain usable. Disable connection multiplexing for the initial managed path. For compromise response, first stop the client and block its management access, revoke all compromised generations through Incus, and terminate managed SSH/Herdr control sessions on targets before generating and deploying a replacement. This disrupts console access; report unreachable targets as revocation incomplete and require their isolation or deletion before claiming containment.

Client recreation or lost key state requires explicit credential recovery: inventory owned workloads, revoke their previously managed client generations through Incus, generate a new client identity, and repeat bootstrap. Never accept stale authorization merely because a replacement client has the same name. Unexpected workload host-key loss likewise requires explicit replacement; ordinary reconciliation does not reset trust.

Cleanup removes target machine entries and trust, then revokes its managed authorization if the workload is retained. Full deployment teardown revokes retained workloads before destroying client credential state. Current `herdr client teardown` only deletes the container; implementation must extend it with revocation or refuse deletion when authorization remains, except for an explicitly requested destructive recovery with incomplete revocation clearly reported. Private key deletion cannot erase copies in snapshots/backups: retire those copies under the same secret-retention policy.

## Diagnostics and acceptance criteria

Status should expose deployment ID, identity generation and public fingerprint, target incarnation, authorization generation, expected host fingerprint, and phase (waiting for guest, authorized, trust pinned, probe passed, or retirement pending). Errors distinguish ownership conflict, unsafe file permissions, guest API unavailability, host-key mismatch, authentication failure, and Herdr readiness failure. Never print private key bytes or credential-bearing exec output.

Implementation requires unit tests for generation/idempotence, ownership guards, unsafe paths, public-key parsing, redaction, mutation-free dry-run, target-set changes, and every crash boundary in rotation. Use disposable Incus integration tests to prove:

- two workloads accept the managed identity as `agent`; root and password login remain denied;
- unrelated and console-disabled workloads receive no authorization;
- strict host verification succeeds with pinned keys and rejects a substituted host key;
- changing an address preserves trust, while explicit recreation replaces trust;
- repeat reconciliation and restart preserve the fingerprint;
- partial provisioning and interrupted rotation resume without discarding the active key;
- old keys fail new authentication after retirement and cleanup preserves administrator authorization;
- private keys never appear in images, Nix outputs, plans, diagnostics, or workload files;
- the real pinned Herdr opens workload sessions using the managed SSH settings.

A VM acceptance test follows once guest-agent bootstrap exists. This document adds no runtime behavior; implementation must land the guest contracts, ownership metadata, runtime driver, Herdr integration, and lifecycle tests before managed SSH is advertised as available.
